# WeFood 产品与技术设计

- 创建日期：2026-10-26
- 修订日期：2026-10-28
- 状态：P1/P2/P3 应用功能已实现（2026-10-28）；真机验证、备份恢复演练与 N150 部署尚未完成。美团订单读取环节已取消。

> 实现现状见：`docs/功能规格/WeFood记忆库.md`
- 使用场景：用户和伴侣、朋友准备外出吃饭或点外卖时，找回吃过的好店与好菜；吃完后方便保存真实感受，并向朋友分享精选内容。
- 决策方式：普通产品与技术取舍采用本文推荐方案；涉及账号安全、外部付费、数据外传或核心目标变更时，再由用户决定。

## 1. 已确认需求

1. 服务名为 WeFood，独立账号登录，像 WeMusic、WeAuto 一样自托管。
2. 当前由用户维护自己的库，未来和女朋友共用账号维护；同一账号支持多设备同时登录。
3. 未来朋友可以使用自己的账号，或者免登录查看用户分享的内容。
4. 私人库支持店铺、菜品、就餐经历、个人评价、标签和备注。
5. 用户在手机网页手动添加和维护记录，可上传菜品与就餐照片，不依赖任何外部消费平台账号。
6. 标签采用“常用分类＋自定义标签”。
7. 分享包含选中的店铺、推荐菜品和点评，采用发布快照，不自动跟随私人记录变化。
8. 分享可设置若干天、若干个月或永久，并可以提前撤销。
9. iPhone、安卓均需方便编辑和查看；手机是主要使用场景，电脑仅适配。
10. 按 2026-10-28 用户决定，彻底移除美团账号连接、订单读取、历史订单导入、自动同步及相关验证环节，不列入后续待办。

## 2. 产品定位与范围

### 2.1 定位

WeFood 是私人饮食记忆库，不是另一个大众点评，也不是以消费图表为主的账本。

优先级：今天吃什么 → 到店点什么 → 吃完留下记忆 → 分享推荐 → 回顾与统计。

三个核心问题：

- 今天想吃清淡的，有哪些我们吃过、喜欢的选择？
- 这家店上次哪个菜值得再点，哪个不合口味？
- 我们以前在哪里吃过，这些经历能否在自己的记忆库中方便找回来？

### 2.2 第一期包含

- 登录、多设备会话、独立账号数据隔离、邀请注册。
- 手动维护店铺与菜品档案、就餐时间线、同行者与分人评价。
- 分类、自定义标签、搜索、筛选、可解释的选店建议。
- 手机快速记录、菜品与就餐照片、草稿和失败恢复。
- 多店/单店分享、快照更新、有效期、续期与撤销。
- 基于用户记录的简单统计、WeFood 自有数据导出与备份。

### 2.3 范围之外

- 美团或其他消费平台账号连接、App/网页订单读取、接口采集、历史订单导入、定时拉取及订单截图自动解析；这部分已取消，不是暂缓。
- 原生 iOS/安卓 App、复杂好友关系、群组权限、社交信息流。
- 自动替用户写真实口味评价。
- 平台支付、代下单、代核销。
- 默认公开整个私人库、开放注册、跨账号共同编辑。
- 第一版离线多设备编辑与自动冲突合并。

仍可记录堂食和外卖的真实体验；“外卖”只是手动选择的就餐方式，不代表接入外卖平台。

## 3. 核心方案与取舍

| 决策 | 备选 | 采用与理由 |
| --- | --- | --- |
| 记忆组织 | 店铺收藏夹 / 就餐经历驱动 | 就餐经历驱动，能保留不同日期、菜品及个人口味；店铺、菜品仍有独立档案 |
| 记录负担 | 完整表单 / 快速记录后补充 | 先记店铺及主要感受，其他内容可后补，减少每次维护成本 |
| 评分 | 单个星级 / 分人评价与再吃意愿 | 分人评价，使用“喜欢、一般、不合口味”和“愿意再吃”；不压成一个平均分 |
| 标签 | 自由标签 / 混合 / 全结构化 | 混合，常用项便于筛选，自定义项保留个人表达 |
| 手机客户端 | 响应式网页 / 原生 App | 手机优先网页＋可安装 PWA，不要求下载安装 |
| 推荐 | 黑盒模型 / 规则解释 | 规则解释，以自己的记录和明确条件为依据，第一版不依赖大模型 |
| 分享 | 实时内容 / 快照 | 快照，避免私人修改意外公开；更新与续期分别操作 |
| 登录 | 无状态 JWT / 服务端会话 | 独立设备的服务端会话，方便单设备退出和撤销，不挤掉其他设备 |
| 数据库 | 外部数据库 / SQLite | SQLite，适合单机和小规模个人服务，减少部署负担 |

数据来源不再做平台接入方案对比，按用户明确决定仅使用主动填写和上传的内容。

## 4. 数据模型

所有私人业务对象归属 `owner_id`，跨账号不得仅靠前端隐藏实现隔离。

| 对象 | 主要职责 |
| --- | --- |
| `User` | 独立账号、状态、密码摘要；不与其他项目共享密钥或用户库 |
| `Session` | 每次设备登录的独立会话、失效时间、最近使用与撤销状态 |
| `Person` | 库内口味人物，例如“我”“女朋友”；不是必须注册的用户 |
| `Restaurant` | 具体店铺/分店，名称、手填地址/坐标、备注、营业状态及更新时间；可保存用户提供的店铺链接，但不抓取内容 |
| `Dish` | 店铺下的菜品，名称、规格/变体、常用标签；不跨分店盲目合并 |
| `Meal` | 一次就餐，时间、堂食/外卖、同行者、可选金额和备注 |
| `MealDish` | 该次实际菜品、数量、规格、吃过与否、当次特点与附件 |
| `Opinion` | 人物对店铺或当次菜品的感受、再吃意愿和点评 |
| `Tag` / `TagLink` | 常用分类、自定义标签、作用对象；支持合并同义标签 |
| `Attachment` | 用户上传的私人照片、归属、处理状态、保留策略与授权访问 |
| `Share` / `ShareRevision` | 分享标识、到期时间、撤销状态、完整快照版本和所选媒体 |

不设计外部订单、套餐快照、订单关联、来源连接、导入任务或平台同步数据表。

### 4.1 关键约束

- 账号与评价者分开。共用账号能分别记录两个人的口味，但不能据此可靠审计是谁实际操作。
- 没评价不等于一般、不喜欢或没吃过；这些状态分开保存。
- 档案中存在的菜品不等于本次吃过；只将用户明确选择的菜加入本次记录。
- 就餐时间来自用户填写；默认当前时间，可以补录过去经历，未知时间不编造精确值。
- 堂食/外卖保留在评价上下文，同一道菜的配送体验不直接覆盖堂食结论。
- 金额可选，以最小货币单位整数保存；没填金额不视为零消费，未知人数不估算人均。
- 店铺同名不代表同一分店；候选重复只提示，由用户确认，不自动合并。
- 保存采用幂等请求标识，弱网重试或重复点击不会重复创建一顿饭。

## 5. 手机页面与操作

### 5.1 导航

底部四个入口：吃什么、记忆库、记录、我的。分享管理与账号设置放在“我的”，不设置外部平台连接或订单管理入口。

采用单列内容卡片、清晰文字层级和少量食物图片。先以浅色、暖中性色、低强度强调色为视觉方向；颜色、间距和圆角统一用语义 CSS 变量，具体值由原型校验，不使用大面积辉光或重动画。

### 5.2 吃什么

- 顶部选择堂食/外卖、这次同行的人，并点选清淡、辣、预算等条件。
- 默认检索自己的记忆，不默认调用外部榜单。
- 优先展示熟悉且符合口味的店；突出推荐理由、必点菜、注意事项和最近去过的时间。
- 例如：“你们都愿意再吃；清淡；上次必点：清蒸鱼；女朋友不喜欢：凉拌木耳”。
- “换一批”只在符合条件的候选中调整顺序，不暗中放宽条件。
- 无结果时明确指出限制，并提供主动放宽条件或查看未点评店铺的入口。
- 新库不编造推荐，引导添加记得的好店或记第一顿，不要求外部账号授权。

### 5.3 记忆库

- 店铺、菜品、就餐记录三种视图，共用搜索和筛选。
- 搜索覆盖店名、菜名、标签及备注；大列表分页加载。
- 店铺详情先展示值得点/需要避开的菜，再展示分人感受与历史经历。
- 菜品详情展示规格、分人评价和每次体验，不只保留最后一句点评。
- 可先保存店铺、菜品和口味记忆，不强迫用户补出不记得的就餐日期。
- 未点评或资料不完整的手动记录仍可查找，不强制先补齐才能使用。

### 5.4 记录

从已有店铺“再记一顿”，或者新建店铺后记录；复用已有菜品，允许现场新增。

快速路径：选择/添加店铺 → 点选实际菜品 → 标记喜欢或不合口味 → 保存。

- 人物默认沿用本次同行者；不用每道菜反复输入人名。
- 最低记录只需店铺；时间默认当前但可修改，菜品、评价、图片和金额均可后补。
- 主要评价一两次点击即可完成，长点评是可选项；不要求填写完整结构化表单。
- 支持相册上传、拍照、多图和备注；照片作为记忆附件，不自动解析订单或生成点评。
- 未保存草稿保留在当前账号的本机缓存，明确尚未跨设备同步；保存成功后才显示已保存。
- 弱网/提交失败保留输入、提供重试，不丢弃整张表单。
- 多设备编辑采用版本检查；冲突时展示最新内容并保留本次输入，不静默覆盖。

### 5.5 我的

设备会话、口味人物、标签管理、分享管理、统计、WeFood 自有数据导出与账号安全。

### 5.6 移动端基线

- 验收宽度包括 360、375、390、430 CSS px，并检查横屏、放大文字与长中文。
- 主要点击区域至少 44×44 CSS px；支持键盘和屏幕阅读器，不靠颜色表达喜欢/避雷。
- 固定底栏适配安全区和软键盘，不遮挡保存按钮、列表尾部及焦点。
- 上传支持相册、拍照和多图；压缩/纠正图片方向，避免原图拖慢手机页面。
- 浏览器后退保留筛选与滚动位置；访客分享页不显示私人管理导航。
- 优先系统中文字体，不依赖境外字体服务；图标采用一致的 SVG 图标库，不用 emoji。
- PWA 仅缓存公共应用壳；私人 API、分享内容及敏感媒体不进入离线缓存。

## 6. 标签与选店逻辑

### 6.1 标签分层

- 食物特征：口味轻重、油重程度、辣、甜、菜系、分量；未填写保持未知。
- 就餐条件：堂食/外卖、适合聚餐、约会、快餐等；价格来自明确填写的金额或手动档位。
- 个人偏好：由人物评价和再吃意愿表达，不把所有人的喜好压成店铺全局标签。
- 自定义：用户可添加“深夜救命”“下雨想吃”等标签。

食物特征能标在菜品或当次体验上；不能因一道菜清淡就自动认定整家店清淡。归纳出的标签只作为建议，用户接受后才进入明确筛选条件。

### 6.2 推荐

第一版使用可解释规则，不训练复杂推荐模型：

1. 先应用明确的堂食/外卖、预算、口味条件；未知字段不默认为满足。
2. 根据本次人物的喜欢、避雷、再吃意愿，排列候选。
3. 最近刚吃过和很久没想起来的熟悉店，作为可调排序因素，不覆盖用户硬条件。
4. 缺少评价的店明确标为“尚未评价”，不能伪装成已喜欢。
5. 不把一人的偏好冒充“两个人都喜欢”；证据不足时展示已有评价。
6. 展示推荐依据和相关记录，允许用户改筛选条件。

距离属于可选增强项：仅在用户授权定位且店铺坐标可靠时参与筛选；否则不伪造距离，也不长期追踪定位。店铺关门/搬迁由用户维护；用户提供的外部链接仅用于跳转，不自动采集内容。

## 7. 手动记录数据流与边界

### 7.1 数据流

用户填写店铺/菜品/经历与上传照片 → 前端保存草稿和校验 → 认证及归属检查 → 服务端校验、幂等写入 → 私人记忆库 → 筛选推荐/选取内容发布快照。

- 所有内容来自用户主动填写、选择或上传，不访问消费平台账号、订单、网页或接口。
- 以前吃过的店和菜可以分次补记；记不清的时间、菜名、金额保持空值，不强迫一次整理完整历史。
- 有就餐经历的数据进入时间线；只有店铺或菜品档案的记忆可用于查找和口味筛选，但不虚构就餐次数与时间。
- 已保存数据在账号内跨设备可见；本机未提交草稿不能显示成其他设备已收到。

### 7.2 保存与照片处理

- 前后端均校验字段长度、有效日期、非负金额及关联对象归属。
- 重复提交使用同一幂等标识；保存成功返回实际记录和版本号。
- 图片上传可以重试或移除，失败不丢失文字内容；未关联照片按保留策略清理。
- 店铺名相同只提示候选分店，不因名称相同自动覆盖。
- 网络失败保留输入；服务端拒绝保存时展示具体原因，不显示虚假的“已保存”。
- 多设备版本冲突时保留本次输入，让用户根据最新记录处理，不静默覆盖。

### 7.3 移除边界

美团订单接入不再是启动或上线前提；此前的 P0 接入验证计划已废止。不存在重新授权提示、订单收件箱、来源能力矩阵、平台连接秘密或后台订单拉取任务。

照片上传不是订单导入的替代包装，不配置 OCR、外部订单解析或自动生成口味评价。账号内跨设备数据共享与 WeFood 自有备份保留，不属于已取消的平台同步。

## 8. 分享设计

### 8.1 发布内容

- 可选单家店，也可创建多店合集，例如“周末清淡好店”。
- 发布页先选择店铺、菜品、点评、图片，再预览访客实际可见内容。
- 默认仅选明确标为推荐的菜及其公开点评；避雷信息、人物显示名需要主动选入。
- 快照采用字段白名单，排除账号信息、未选私人备注和未选图片；不直接复制整份私人记录。
- 快照保存文字和媒体版本，不动态引用私人备注或后来替换的图片。
- 访客页是轻量手机单列页面，先看到推荐菜和理由，再看到店铺公开位置/用户提供的链接。
- 免注册、免登录、无登录遮罩；不同账号打开也只能看到发布内容。

### 8.2 时间规则

- 创建时提供 3 天、7 天、1 个月、3 个月、永久，以及自定义正整数天/月。
- 发布前显示具体到期时间，按北京时间展示。
- 天按北京时间的日历日增加并保持时刻；月按日历月增加，月末溢出取目标月最后一天。
- 时间在数据库存 UTC；永久保存空到期时间，不用超远日期模拟。
- 更新快照不重置期限；延长有效期是独立操作。
- 已到期分享可沿用链接续期，明确从当前时间计算新期限；已撤销分享不自动复活，再分享生成新链接。
- 有效期从发布成功开始计算；创建草稿失败不消耗时间。

### 8.3 访问与撤销

- 状态：有效、已到期、已撤销。每次访问由服务端实时判断，不依赖定时清理是否执行。
- 到期/撤销后只显示状态说明，不展示文字、图片、菜名或详细页面元信息。
- 随机高熵链接不是好友身份认证：知道链接的人均可访问，也可继续转发。
- 所有分享图片也经有效性检查，不能通过公开静态图片 URL 绕过到期。
- 快照和分享媒体返回禁止缓存策略；服务端和 CDN 不缓存私人分享内容，PWA 不缓存。
- 使用 `noindex` 和限制 referrer 泄露；链接 token 在访问日志中脱敏。元信息只放通用标题，减少外部链接预览缓存泄露。
- 用户已截图、下载或第三方已保存的内容不能撤回，发布页说明这一边界。
- 私人原记录删除不自动改变已发布快照，删除前提示并提供同时撤销相关分享的选项。

## 9. 统计与归纳

- 月度已记录就餐次数，堂食/外卖占比，常去店铺，愿意再吃的菜，未点评记录数量。
- 消费统计仅包含明确填写金额的经历，显示有金额/缺金额的记录数量，不把缺金额记为零消费。
- 显示记录时间范围，明确这是用户已记录的经历，不声称覆盖全部历史消费。
- 用列表、横向条形图及简单趋势图，不以复杂看板压缩手机阅读空间。
- 归纳结论基于真实评价，例如“最近三次都觉得偏咸”，附原记录；缺证据时不生成确定性结论。
- 本期不把模型生成的总结当成用户的真实点评；外部模型不是必要依赖。

## 11. 技术架构与模块影响

### 11.1 选型

- 新项目采用 Node.js 24、TypeScript、Express、SQLite；前端 React＋Vite，手机优先路由与页面。
- 独立同源网页/API，避免拆成多个服务和跨域登录；不是复用其他项目的业务代码。
- SQLite 开启外键与 WAL，数据库迁移版本化；照片在受保护持久化目录，数据库存元数据。
- 不引入外部平台采集器、OCR、订单适配器及任务调度基础设施；照片处理限制大小与并发，不阻塞正常查询。

### 11.2 模块边界

浏览器页面 → 认证/归属检查 → API → 业务服务 → 数据库/受保护照片。

公开分享入口 → token 与期限检查 → 白名单快照和授权媒体；不走私人档案查询接口。

规划模块：`auth`、`restaurants`、`dishes`、`meals`、`opinions`、`tags`、`shares`、`media`、`stats`。

规划 API 范围：`/api/auth/*`、`/api/sessions`、`/api/restaurants`、`/api/dishes`、`/api/meals`、`/api/tags`、`/api/shares`、`/api/stats`。公开页面为 `/s/:token`，共享媒体走同样的有效性校验。

不保留 `/api/imports`、`/api/connections` 或 `/api/sync-runs` 等平台接入路由。

### 11.3 登录与安全

- 账号用户名/密码登录；首个账号通过一次性初始化创建管理员，之后邀请注册，默认没有公开注册入口。
- 密码使用经验证的密码哈希库和参数，不保存明文；登录限频，允许密码管理器与粘贴。
- 会话使用独立随机 token，数据库只存摘要，Cookie 设置 HttpOnly、Secure、SameSite；写请求验证来源并防 CSRF。
- 当前设备退出只撤销当前会话；支持设备列表、撤销某设备、退出全部设备，改密码撤销旧会话。
- “设备名称”仅为用户辨认标签，不宣称可靠设备指纹；共用账号没有分人权限隔离。
- 照片私有，限制类型、大小、数量及解码资源；清理 EXIF，不直接执行上传内容。
- 用户提供的店铺链接只保存并供主动跳转，限制为有效 HTTP/HTTPS 地址，不执行脚本、不在服务端抓取链接。
- 不收集消费平台账号、密码、Cookie、token 或人脸验证资料。
- 上传照片默认不外传；付费服务和数据外传必须另行取得用户同意。

### 11.4 自托管部署

参考既有 Node＋SQLite 服务，但不直接复制其默认密钥、端口、开放注册和全设备退出语义。

- 目标沿用现有 CI → Release/R2 → webhook → deploy-agent 管理模式；不手动 SSH 启停 N150 服务。
- 新项目使用独立应用目录、依赖目录、数据目录、密钥、域名和端口；实际基础设施值在部署接入时核实，不编造。
- 发布包不包含 `node_modules`；目标机用匹配的 Node 版本安装依赖，避免 SQLite 原生模块 ABI 不一致。
- 持久化 `data/`、上传、数据库和密钥不被部署覆盖；备份包含数据库、媒体及恢复所需密钥，备份本身受保护。
- 数据库采用一致性备份，不直接复制运行中的 WAL 主文件当完整备份；验收包括恢复演练。
- 对外提供不泄露私人数据的健康检查；部署脚本遵守已有进程/锁规范，不引入子进程继承锁导致队列死锁。

## 12. 风险等级与处理

| 风险 | 等级 | 影响与处理 |
| --- | --- | --- |
| 跨账号或分享媒体绕过鉴权 | 高 | 全库/已到期内容泄露；服务端归属检查及正文/媒体成对验证 |
| 记录负担导致遗漏经历 | 中 | 无自动补录；快速保存、复用已有店铺/菜品、照片及后补信息，不强迫完整表单 |
| 同名店或重复提交 | 中 | 错误归纳/重复经历；分店候选确认，保存请求幂等 |
| 多设备同时修改 | 中 | 点评被覆盖；版本检查和冲突恢复 |
| 记录不完整却统计为全部消费 | 中 | 分析误导；明确记录范围和缺金额数量 |
| 共用账号没有分人权限 | 低至中 | 两人能改全部私人记录；人物只是评价维度，不是权限模型 |
| 分享可转发、已保存内容不可撤回 | 中 | 超出预期传播；发布提示、期限、撤销，不能承诺截图撤回 |

移除平台接入后不再存在必须先通过美团验证的上线门槛。代价是经历需要主动记录，不再承诺自动找回全部历史。

## 13. 验收标准与验证计划

### 13.1 可观察验收

1. 两台手机登录同一个账号，一台保存就餐评价，另一台刷新看到同一记录；退出一台不影响另一台。
2. 同一家店能分别看到“我喜欢”和“女朋友不合口味”，不会被一个平均分抹掉。
3. 选择“清淡＋堂食＋本次人物”后，看到符合已有记忆的店、推荐菜和依据；没结果时不会暗中放宽条件。
4. 不提供外部账号、订单或导出文件，也能新建店铺、添加菜品、保存就餐和点评。
5. 同一家店“再记一顿”能复用原店铺和菜品；没选为本次吃过的菜不成为本次评价证据。
6. 手机上传照片并填写备注，弱网提交失败后输入仍在，重试不重复创建经历。
7. 手机免登录打开分享看到所选内容；修改私人点评不会改变快照，主动更新后才变化。
8. 分享到期/撤销后正文、接口和图片均不可访问；更新不重置期限，已到期链接可续期。
9. 两个独立账号通过 URL、接口或媒体标识均不能访问对方私人数据。
10. 多设备同时修改同一记录时出现冲突提示，双方输入不会被静默丢弃。
11. 备份恢复后，店铺、菜品、经历、评价、照片和分享规则仍可读取。
12. 页面没有美团授权、订单导入、重新连接提示；服务端没有平台订单读取及后台拉取任务。

## 18. 店铺菜品来源与记录显示（2026-10-28 追加）

用户需要获取具体分店的菜品，勾选实际吃过的菜并分人点评，下次可区分好吃与避雷；不是仅想输入菜名，也不是恢复私人美团订单读取。

### 当前缺口与数据来源核查

记录页仅请求私人库 `/dishes?restaurantId=内部店ID`，腾讯地图只提供地点基础资料，地图收录店不会自动带入菜单。空列表、请求失败及换店加载未明确区分，容易误认为店里没有菜。

- 美团官方 `food/list` 动态正文已核实：按APP方门店ID查询、分页小于200，属于外卖商品能力，不代表完整堂食菜单。新版 `wmoper/ng/food/queryFoodList` 和 `waimai/ng/dish/food/listAll` 官方索引标注需要业务授权/管理API，正文访问未取得，不能推断消费者可查任意店。
- 大众点评企业版到餐API正文已核实：需要申请token/sign/aesKey/entId；其中标题“商家菜品列表”的返回实际为店铺列表，没有文档化完整菜单，团购标题也不是菜品清单。
- 高德官方搜索POI正文明确 `extensions=all` 的 `tag` 可含餐馆特色菜，未承诺覆盖率、完整菜单、单菜价格或规格。需独立Web服务Key，并按店名/地址/位置确认分店匹配，不能拿腾讯ID直接当高德ID。
- 官方现有个人开发者MCP入口有线索，但完整菜单工具和访问权限未验证，不把“可以入驻”算作菜单可用。第三方声称可爬取不能作为来源合法性和完整性证据，不绕过登录/反爬。

完整菜单的可行路线是餐馆公开菜单/点餐页面或获得授权的菜单服务；取决于具体店铺。菜单照片/截图识别可做保底，但需要核对，仅表示拍到的菜单页；不能替代自动获取目标。高德特色菜只能作为候选补充，不能标“全部菜品”。本轮未配置新第三方Key、注册实名账号、付费或连接消费账号。

### 方案、状态与实施范围

外部菜单候选与私人Dish分开，保留来源、分店、时间及完整性状态。用户勾选后才创建/映射私人菜品并进入实际就餐，未吃过不生成评价；标签、必点/避雷、分享继续以自己的点评为证据。外部更新不覆盖私人点评。

## 20. 每道菜直接评价（2026-10-29 追加）

- 状态：已实现并上线（2026-10-29），生产版本 `770fde2` 已核对；现状见 `docs/功能规格/WeFood记忆库.md` 第12章。目标是用户在菜名旁直接点好吃/一般/不好吃，不再先勾选、再到下方寻找评价。
- 采用每道菜的内联评价卡片（已录入、新增、公开参考同一组件），每个同行人物各一组三档按钮。下方独立感受区只保留整家店评价，不重复菜品评价。
- 数据流：点某菜某人的三档按钮 → 同一次草稿状态更新完成选中菜、记录来源（新参考菜）和写 feeling → 创建新菜时迁移评分键 → 本次就餐保存。复用原like/neutral/dislike值，不改变接口或历史点评。
- 不把未评价默认成一般，浏览候选不创建菜；再点当前评分可清空评分但仍保留吃过选择、再吃意愿和备注。独立取消吃过会清该菜本次所有人物评价。可以只记录吃过不评价，不能强迫对没吃的菜评分。
- 名称及规格区分；同名无规格已有菜与参考只展示一个评价卡片、复用同一ID。来源失败或加载时保留已选草稿与来源，未知资料不展示上一店评分；保存期间禁止编辑。
